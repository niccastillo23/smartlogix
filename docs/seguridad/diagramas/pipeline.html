Pipeline de integración continua y controles de seguridad automatizados

SmartLogix · GitHub Actions (.github/workflows/ci.yml) · se ejecuta en cada push a main/v2 y en cada pull request

1. Commit / PR

Control de versiones con Git y revisión por pull request
Secretos fuera del repositorio: JWT_SECRET en GitHub Secrets; .env ignorado
Revisión de secretos; rotación pendiente del secreto antiguo (INC-02)
Ley 21.719 art. 14 quinquies (confidencialidad)
→

2. Backend (4 módulos)

Pruebas unitarias e integración: JUnit 5, Mockito, MockMvc (134 pruebas)
Cobertura JaCoCo ≥ 60 % de líneas por módulo
SpotBugs + FindSecBugs: sin hallazgos de prioridad 1 sin tratamiento documentado
OWASP A06, A08
→

3. Frontend

Vitest + RTL: 55 pruebas, cobertura de statements
ESLint con eslint-plugin-security
npm audit --omit=dev: bloquea critical/high en producción
Build de producción de Vite
OWASP A06
→

Puerta A: calidad

Falla si hay pruebas en rojo, cobertura < 60 %, prioridad 1 de SpotBugs o vulnerabilidad crítica/alta en producción
Bloquea el merge a main
Ley 21.719 art. 14 quinquies (verificación periódica)
→

4. Stack en Docker

docker compose build de los 5 contenedores (Dockerfile multi-etapa, usuario no root)
Microservicios sin puertos publicados; JWT obligatorio entre servicios
Espera de disponibilidad extremo a extremo (esperar_stack.sh)
OWASP A01, A05
→

5. E2E y API

Playwright: 5 flujos de interfaz (UI-01 a UI-05) y 6 pruebas de API
Valida el control de acceso, el error de login y el bloqueo por intentos
Reporte HTML y JSON como artefacto del pipeline
→

6. DAST

OWASP ZAP baseline sobre el frontend desplegado
Cabeceras de seguridad: CSP, COOP, CORP, Permissions-Policy
OWASP A05
→

Puerta B: seguridad

Falla si ZAP reporta alertas de riesgo alto
Bloquea el merge y conserva el reporte
Análisis SonarQube local (ver docs/seguridad/sonarqube)
Etiqueta normativa Criterio de la asignatura y de la normativa aplicable que cada control verifica. Los controles SAST con SonarQube se ejecutan en un servidor local y no bloquean el pipeline remoto.
Trazabilidad: cada puerta corresponde a un requisito del Encargo 2 (REQ-CAL-01, REQ-CAL-02, REQ-SEG-06, REQ-DEP-01) y a un caso de la batería ejecutable (CP-14, CP-15, CP-16, CP-17) y de las pruebas E2E.
